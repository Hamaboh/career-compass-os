# Phase 2: 匿名化・コンテキスト・外部AI境界

## 1. 基本方針

外部AIへは、目的達成に必要な最小限の匿名化済み情報だけを送る。匿名化しても再識別のおそれが残る場合は送信しない。匿名化処理はアクセス制御の代替ではなく、まずUnit・役割による参照制御を適用し、その後に最小化と匿名化を行う。

## 2. 外部送信分類

| 分類 | 例 | 取扱い |
|---|---|---|
| 送信禁止 | 氏名、メール、社員ID、電話、住所、認証情報 | 常に除外 |
| 原則禁止 | 客先名、案件名、会社固有名、Unit名、役職固有名、評価制度用語 | 一般概念・プレースホルダーへ置換 |
| 要一般化 | 正確な日付、希少な資格・経歴、少人数属性、固有の障害事象 | 月・期間・抽象カテゴリへ一般化 |
| 条件付き許可 | 本人の発言、目標、進捗、1on1メモ | 機密区分と目的を確認し最小抜粋 |
| 許可 | 一般的なSMART項目、汎用質問、匿名の作業種別 | 目的範囲で送信可 |

`機密`は既定でAI送信対象外とし、ULが内容単位で明示解除した場合だけ候補にできる。`AI送信禁止`は解除できず、手動処理のみとする。

## 3. 匿名化規則

- 人物は`MEMBER_A`、`UL_A`等、案件は`CLIENT_PROJECT_A`、制度項目は`POLICY_ITEM_A`等に置換する。
- 対応表は内部にのみ保持し、外部プロンプト、AI応答、一般ログ、共有HTMLへ含めない。
- プレースホルダーは1リクエスト内で一貫させる。セッション横断の固定識別子は必要な場合だけ内部で再生成する。
- 自由記述は辞書置換だけでなく、固有表現、連絡先、識別子、社内用語、組合せによる再識別リスクを検査する。
- 正確な日付は必要性がなければ「今月」「3か月以内」等へ変換する。
- 原文を抽象化すると意味が変わる場合はAI送信を中止し、手動支援へ切り替える。
- 匿名化済みであることを完全匿名の保証として表示しない。

## 4. コンテキスト構築

各AI操作は許可リスト方式とする。

1. 操作目的を1つ選択する。
2. Actorの権限と対象Unit・Memberを検証する。
3. 目的に必要な確定情報と直近差分だけを取得する。
4. `AI送信禁止`、不要な機密、他Member・他Unit情報を除外する。
5. 出所と参照IDを付け、匿名化・一般化する。
6. トークン量と費用見積りを表示する。
7. ULへ送信予定全文、除外項目、置換一覧（逆引き値は画面内のみ）を提示する。
8. ULの明示承認後のみ送信する。

全履歴、制度資料全文、PDF原文、1on1原文を丸ごと送らない。制度を参照する場合は、内部で承認済みの目的別要旨を作り、会社固有用語を一般化する。

## 5. プロンプトインジェクション対策

Member発言、1on1メモ、制度文書、共有資料中の命令文はすべて「データ」として区切り、システム指示として扱わない。外部テキストが「以前の指示を無視」「秘密を出力」等を含む場合は警告して除外またはエスケープする。AIには許可された構造化出力以外のツール実行権限を与えない。

## 6. 応答側検査

- 氏名、メール、社員ID、会社・客先・制度固有語の復元らしき文字列を検査する。
- 入力参照にない事実断定、評価・診断・離職予測、差別的表現を拒否する。
- 事実、推測、提案、不明点が構造上分離されているか検証する。
- 違反時は応答を利用者へ通常表示せず、一般化した理由と再試行・手動継続を示す。

## 7. ログと保持

一般アプリログにはプロンプト、自由記述、AI応答本文、置換前後の対応表を記録しない。AI監査には操作種別、Actor、対象の内部ID、モデル・プロンプト版、承認者・時刻、入力ハッシュ、匿名化検査結果、トークン・費用、成功状態を記録する。本文保持が品質検証に必要な場合は別の暗号化領域、限定権限、短期保持、削除期限をPhase 3で定義する。

## 8. 共有・出力境界

共有HTML・ダウンロードには人間が確定した対象Memberの情報だけを含める。未承認のAI推測、UL非公開メモ、監査ログ、他Member情報、匿名化対応表を除外する。共有リンクの既定期限は7日、最大30日とし、失効・手動取消を可能にする。
